# Bug 65: Byte classes merge bytes that assertions tell apart

## Bug summary

- **Pattern**: `(?m:^)ab|q…q`, `xa(?m:$)|q…q`, `\b{start}ab|q…q`,
  `xa\b{end}|q…q`, where `q…q` is 130 literal `q` (any second branch
  that brings the pattern to 128 NFA states).  Default settings.
- **Input and result**:

  | Pattern | Input | Expected | Actual |
  |---|---|---|---|
  | `(?m:^)ab\|q…q` | two spaces, `\n`, `ab` | `true` | `false` |
  | `(?m:^)ab\|q…q` | `\n`, space, `ab` | `false` | `true` |
  | `xa(?m:$)\|q…q` | `xa  xa\n` | `true` | `false` |
  | `\b{start}ab\|q…q` | `zz ab` | `true` | `false` |
  | `\b{start}ab\|q…q` | `- zab` | `false` | `true` |
  | `xa\b{end}\|q…q` | `xaz xa-` | `true` | `false` |

- **Affected tiers**: 1 and 2 as observed (Tier 1 is the default for
  these patterns); every DFA tier uses the same table.
- **Found by**: the Tier 2 audit sub-agent, reading
  `compute_byte_classes()`.  No test, fuzz seed or sweep hit it.

## Root cause

From 128 NFA states on, the DFA tiers index their transition tables by
*byte equivalence class* instead of by byte.  A transition computed for
one byte is then reused for every byte of its class.  That is only sound
if the computation gives the same result for all of them.

The computation does two things with the byte: it lets consuming states
consume it, and it evaluates assertions with the byte as their *next*
byte (a parked `\b` or `(?m:$)` being resolved) or as their *previous*
byte (the closure after consuming, which evaluates `(?m:^)`).  The class
signature covered the first exactly.  For the second it had its own,
separate rule:

```rust
let has_any_deferred = /* any WordAscii, WordAsciiNegate or EndLF */;
...
if has_deferred_assert {
    sig.push(if is_word_byte(b) { 1 } else { 0 });
}
```

Three things were wrong with it:

- `(?m:^)` (`StartLF`) was not in the list, and reads "is the previous
  byte `\n`".
- `(?m:$)` (`EndLF`) was in the list but got *word-ness*, which does not
  separate `\n` from a space.
- `\b{start}` and `\b{end}` were added to the engine later and never
  added to the list.

So `\n` shared a class with other non-word bytes, and for `\b{start}` /
`\b{end}` word and non-word bytes shared one.  Whichever byte of the
class came first decided the cached transition for all.

## Investigation narrative

1. The sub-agent's report gave patterns, inputs and the two source
   locations.  All six rows above reproduced on Tier 1 with the default
   settings.
2. The same patterns without the 130-byte branch are correct: below 128
   states the table is indexed by byte.
3. Forcing the classes on for every pattern (the threshold set to 0 in
   the source) and running the existing suite made 2 tests give wrong
   answers; the fuzz seeds 0–1999 found nothing, because the generator
   only emits `\b` and `\B`.

## Fix

What an assertion reads from the bytes around it is declared once:

```rust
impl AssertKind {
    pub(crate) const fn byte_props(self) -> ByteProps {
        match self {
            Start | End => ByteProps::NONE,
            StartLF | EndLF => ByteProps::LF,
            StartCRLF | EndCRLF => ByteProps::LF.union(ByteProps::CR),
            WordAscii | WordAsciiNegate | WordStartAscii | WordEndAscii => ByteProps::WORD,
        }
    }
}
```

`compute_byte_classes()` takes the union over the pattern's assertions
and puts `ByteProps::of(b) ∩ that` at the front of each byte's signature.
It no longer takes a flag from its caller.

The match is exhaustive, so a new kind cannot be added without an entry.
Two tests tie the declaration to `eval()` over every kind, position flag
and pair of bytes: replacing a byte by another with the same declared
properties never changes the outcome (the declaration is sufficient),
and every declared property changes some outcome (it is not wider than
needed, which would cost classes).  The list of kinds they iterate over,
`AssertKind::ALL`, is generated by the macro that defines the enum, so
it cannot miss one either.

Two more hand-written summaries of an assertion were found in review and
tied to `eval()` the same way:

- A DFA state remembers only the word-ness of the byte that entered it
  and resolves parked assertions with a stand-in byte.  A test checks,
  for every kind the DFA tiers defer and every previous byte, that the
  stand-in gives the same outcome; another checks that the deferrable
  kinds are exactly the ones that can ask to wait.
- Tier 4 evaluated `^` and `(?m:^)` with its own conditions.  It now
  calls `eval()`.

The threshold is now `RegexConfig::byte_class_min_states` (hidden from
the docs, default 128).  The `match_tests!` runner repeats each of its
three builds with the classes forced on.

## What was hard

- The pattern has to be large and use one of four assertion kinds, and
  the input has to present two bytes of a merged class in the right
  order.  Nothing in the suite or the fuzzers combined the three.
- The buggy rule was a second, hand-written summary of what `eval()`
  reads, in another part of the file.  Each was right when written; they
  drifted apart when assertion kinds were added.
- For `(?m:$)` the rule had the right kind and the wrong property, which
  reads as handled.

## Tooling ideas

- Thresholds as test parameters, again (see Bug 64): done here for byte
  classes, in the test runner and as `RETHOC_BYTE_CLASS_MIN_STATES` for
  the CLI tools.  CI now runs the fuzz range and every sweep a second
  time with both thresholds at their extremes.
- `rethoc sweep assert-edges`: every assertion kind on either side of a
  repetition.  With the old rule and the classes forced on, 325 of its
  1,792 runs fail; at the default threshold none do, which is how the
  bug stayed hidden.
- The fuzz generator emits only `\b` and `\B`.  Adding `(?m:^)`,
  `(?m:$)`, `\b{start}` and `\b{end}` would cover this class of bug at
  random, but changes what every seed generates, so the known-clean
  ranges and the slow-seed list would have to be redone.  Not done here.
- Other tables derived from the pattern by their own walk (prefilter,
  `compute_can_reach_match`, the tier analyses) have the same shape as
  the old rule.  Bug 60 was one of them.
- Bugs like this one depend on what the DFA cache already holds: the
  first byte of a class to reach a state decides for the others.
  `brute` and `fuzz` share one `MatcherMemory` across inputs and so find
  them, but the input they print may pass when run alone.  They now
  check that and say so, and `shrink` runs every candidate on fresh
  memory, so that what it prints fails on its own.
